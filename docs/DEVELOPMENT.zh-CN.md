# 开发文档

[English](DEVELOPMENT.md)

## 本地运行

需要 Python 3.10+、Node.js 20+ 和支持 WebGL 2 的浏览器。重新生成场景缓存时还需要 Google Chrome。

```sh
git clone https://github.com/sldyns/PKU-3D.git
cd PKU-3D
npm install
npm run setup
npm run build
npm run dev
```

`setup` 从 GitHub Releases 下载对应版本的场景和纹理，并核对哈希。`build` 使用匹配的场景缓存生成 `dist/`。在浏览器中打开 `dev` 输出的本地地址。

## 目录

| 目录 | 内容 |
| --- | --- |
| `app/src/` | 渲染、建筑模型与交互 |
| `app/data/` | 可编辑的校园数据与场景元数据 |
| `app/tools/` | 场景构建工具 |
| `app/tests/` | 运行时回归检查 |
| `scripts/` | 资源准备、本地服务与打包 |

| `dist/` | 构建产物，不提交到 Git |

部分内部模块保留数字后缀，以维持缓存兼容；发布版本统一由 `VERSION` 定义。

## 修改与验证

修改界面或文档后运行 `npm run build`。修改建筑、植被等场景输入后，运行 `npm run build:scene` 重建缓存，并在浏览器中检查受影响的建筑和交互。

`npm test` 按 `app/tests/suite.json` 的明确清单检查解码、实例传输、可见性、绘制复用和选定模型修补；[测试范围](development/testing.md) 区分公共回归与本地历史脚本。画面验收和性能对照需单独完成，详见[性能说明](development/performance.md)。

## 正式渲染后端与画质

正式版使用 WebGL 2，新用户默认高画质，并恢复有效的已保存选择。高画质保留完整网格、原始纹理、阴影与反射目标，在已验证的硬件配置中使用四重 MSAA。光影面板里的中、低画质是用户主动选择的画质与性能取舍，不能用这些档位的结果宣称高画质渲染提速。

较慢的 WebGPU 实验不进入正式包，研究结果和中间截图留在本地。局部 GPU 耗时下降不能证明完整程序更快，也不能证明真实交互达到稳定 60 FPS。

高画质可在有界的空闲回调中，准备独立、固定为 16 MiB 的可见性内存。批量分组判断和连续片段收集保留原来的双精度运算、导入的 `Math.hypot`、细节阈值与实例顺序，既有 SIMD 分组指令体保持不变；内核源码见 `app/tools/visibility-high-batch.wat`。只有当前场景代次下由 Engine 拥有的数据可以进入该路径。未准备完成、不支持的状态或失败继续使用原选择器。场景失效、切换画质、销毁或上下文丢失时，释放全部类型数组引用并取消待执行任务。高画质仍使用原来的 GPU 实例上传和两帧准入队列。

实验项默认关闭，只有明确的 `state.highVisibilityBatch === true` 才允许准备或使用该路径；关闭时释放内存并继续使用原标量路径。光影面板中的选择独立保存，不改变画质预设。启用路径的 CPU 收益不能表述为已经通过综合帧间隔验收。

地名标签随实际提交的镜头更新。先读取面板范围并计算本次标签，再更新 DOM；计算期间保留仍需显示的标签，避免隐藏操作与布局读取让键盘焦点丢失。仅隐藏退出本次选择的标签，并且只写入发生变化的位置、可见性与当前选择属性。每次读取最新数据，不缓存可能被外部修改的地点或面板信息。

## 第一人称漫游

`app-v29.js` 中的步行控制器把起点投影到既有道路图。手动移动限制在连通道路的宽度内，并避开地图建筑轮廓；这些轮廓检查不覆盖每一处围墙、树木、阶梯和门禁。自动步行沿用同一路网，遇到建筑轮廓重叠时暂停，不补画不连通的道路。视点位于地形上方 1.68 米，退出时还原此前的镜头与标签设置。窗口失焦、页面隐藏及 WebGL 上下文丢失时清除移动输入。这部分修改不改变预烘焙场景。

在页面可见的动画帧中，先推进移动输入和路线播放，再检查 GPU 两帧队列是否允许提交。保留时间步长上限、移动子步和中断后的输入时钟重置，不能因队列已满而丢掉正常移动时间。浏览镜头遵循 `prefers-reduced-motion`，用户要求减少动态效果时直接切换到目标视角。

连续滚轮输入按输入时刻推进缩放目标，在两次接受渲染之间只保留一个待提交镜头。反向缩放、取消或拖动中断以最后显示的镜头为锚点，避免待提交状态使视角跳变。

## 渲染

生成网页时，校园数据、建筑资料、场景清单和拾取描述分成四个纯数据脚本，使用经典 defer 脚本在主程序前按序执行，让浏览器独立编译数据和程序。主程序在原初始化位置接收各值并清除临时对象。保留字面量语法、原始数字文本、负零、成员顺序及数据后附的可执行适配器；不要再用 `JSON.parse` 封装这些数据，以免额外分配大型字符串。完整源清单仍是缓存校验依据，就绪条件仍包括所有场景和渲染资源。发布哈希和脚本总字节数必须包含所有数据脚本。

硬件支持半浮点颜色缓冲且能保留现有多重采样数量时，表面光照、倒影、雾、玻璃和粒子使用统一的线性 HDR 流程，在最终合成阶段应用接触阴影和一次色调映射。其他设备保留 8 位颜色缓冲与抗锯齿，并在混合反射光前还原显示映射。

水面是水平网格，以变换后的包围盒中心高度确定反射平面。选中或距离镜头目标最近的可见水面决定当前单一平面反射；同时出现多个高度的水面时仍共享这张反射图。树叶使用专用材质路径，保留叶片、顺序和光照方程。

`material-detail.js`、`water-detail.js`、`quality-lod.js` 和行人运行时代码不生成静态场景几何，因此不计入场景输入摘要。建筑、植被和地面模型修改，包括低档位备选网格的生成，仍需重建场景。

构建会通过 `tools/build-water-detail.py` 更新未名湖外岸距离场。它依据现有公开地图岸线，只用于临岸波纹和色泽过渡；不推测水深，也不改变岛岸或其他水面的处理。岸线数据与生成脚本均参与校验，防止缓存过期。

接触阴影使用实际偏轴投影重建视空间坐标，保留原采样分布。天空光和地面反射光按表面方向分配；雨天响应区分材质与朝向，不代表精细的遮雨模拟。

解码块之间延续 7 毫秒上传预算，索引缓冲也计入检查，避免块尾重复等待动画帧。通过 `KHR_parallel_shader_compile` 轮询着色器完成状态，与纹理加载、双工作线程解码和分批上传重叠；完成后才查询编译和链接结果，不支持该扩展时沿用同步校验。材质、扫描纹理、场景资源和着色器程序全部结束后，才进入就绪或失败清理。启动时仍复用相同的着色器阶段；超时、资源销毁或上下文丢失会取消等待并释放临时阶段。实例可见性元数据随解码分块到达时准备，最终就绪前仍校验全部网格缓冲；上下文恢复时重新创建资源。

材质 0、6、21 的不透明专用路径从共享着色器派生，保留纹理采样、导数过滤、材质公式和实例顺序。混合材质或不支持的绘制桶沿用普通路径；添加专用程序时同步维护就绪检查和清理清单。

绘制桶空间索引只为 Engine 管理的几何建立，由明确的 epoch 标记有效期，并在空闲时分步构造。索引未就绪或数据无法安全判断时，沿用原有顺序扫描。外部直接改写实例数组、已编译的包围数据，或修改 bucket Map 成员及顺序前，必须调用 `invalidateBucketIndex()`，并在下次渲染前更新派生的可见性数据与缓存；对象身份和 Map 大小不变不代表索引仍有效。普通可变 Map 不会自动建立索引。

水面 footprint 剔除从支持的静态水平水面推导保守范围，不改变几何。缺少元数据、动画或混合材质、变换不受支持、投影不确定时，沿用原有保守反射路径。保留波纹和过滤余量、反射目标尺寸、更新频率及透明绘制顺序。

可见实例按连续区间批量复制到紧凑缓冲。仅当保守包围范围和细节尺寸上下界能够证明整组记录均通过或均不满足原有阈值时，才跳过逐实例判断；隔离、隐藏植被、路线过滤及无法证明的情况沿用原有检查。被剔除的记录会截断复制区间，缓冲扩容保留此前记录和待复制区间。

## 可选编码与首帧准备合同

可选场景编码仅通过显式批准的 sidecar 接入，且必须匹配准确的烘焙清单和源码摘要。只有 `gzip-meshopt-attributes-v1` 压缩字节数严格小于原格式时才选用；相同或更大时保留原格式。已审查的 94 块候选选用 36 个新编码块（30 个顶点块、6 个索引块），仍保留全部 94 个原 gzip 文件及脚本备选，11 个实例块全部使用原传输格式。这些数量描述该候选，不能硬编码为以后场景的规则。接入保留原始字节 SHA 门禁及生成时的逐字节证明，不改变网格和实例顺序、填充字节、图集像素或画质。

固定两个场景工作线程，每个线程最多一个待解码任务。同一次 worker 消息内先尝试新格式，失败时最多用原格式重试该块一次，最终只发布一个校验完成的结果；原格式也失败时终止场景加载。不增加工作线程池、跨任务重试或新的 HTTP 转脚本恢复策略。`file://` 沿用原脚本嵌入 gzip。官方解码器及其 MIT 许可须为包内真实本地文件，不从远端引导下载。保留既有资源销毁与上下文恢复行为。

显式导入必须拒绝不匹配的父清单、源码包、资源哈希或路径。发布投影保留可选 codec 字段，仅移除原先约定的 bucket 审计哈希。构建与归档依赖由清单明确列出，不扫描目录来发现候选文件。新烘焙清单不含扩展时，即使目录残留新编码资源也使用原格式；旧 sidecar 不能导入不同的烘焙结果。输入未变的缓存复用可以保留仍有效的扩展。归档恢复检查需覆盖两种传输、解码器和许可。较小的网络载荷不代表发布包缩小：该候选在保留全部原资源之外，增加 34,728,843 字节的新编码载荷、解码器和许可，尚未计入元数据。

首帧可见性准备仅做分段的 CPU 空闲工作；时间预算在工作单元之间检查，不保证每次回调都在固定时限内结束。它复用正式渲染的可见性及有序实例流生成器，为主视图和阴影视图提前准备，并复制镜头及可变状态输入，不另写一套剔除算法。完整视图/状态键、viewport 和 Engine generation 全部相同才可采用预备结果；失效或未完成则丢弃并沿用普通路径。数据修改、重新编译、销毁及上下文丢失不得留下可被误用的旧结果。VAO 创建、GL 上传和绘制提交仍只由正式渲染负责，不增加 GL 工作，也不降低细节、分辨率、绘制距离、阴影、反射或抗锯齿。功能和像素通过不能代替正式启动、内存及帧时间对照。

反射视图在全部所需水面资源成功发布后，复用相同的有序 CPU 实例流生成器提前准备。快照同时绑定主视图和反射矩阵、水位、反射目标及剔除开关。资源发布、对象身份或输入变化时，仅丢弃失效的反射结果，保留仍有效的主视图与阴影结果。首次实际渲染会停止排队准备，只采用完全匹配的结果并释放保留的 CPU 数组；GL 上传和绘制提交仍由正式渲染负责。

## 无损首屏数据包

运行 `node scripts/build-startup-codec.cjs`，从当前烘焙场景生成 `app/data/startup-codec-v1.json`。准入记录固定父清单、源码、编码器及每块原输入、压缩候选和解码原始数据的哈希。候选必须逐字节往返一致，并且该块压缩体积至少减少 5%。随后运行 `npm run assets:pack` 并构建网页。`scripts/scene_startup_packs.py` 校验显式准入记录，生成每包不超过 32 MiB 的确定性数据包，不扫描目录发现候选。场景重新烘焙后不能沿用不匹配的旧准入记录。

整数变换使用模运算差分、zigzag 和字节平面，不量化浮点数，也不改变顶点或索引顺序。`app/tools/scene-startup-delta.wat` 的 SIMD 逆变换复用既有固定 512 KiB 转置内存，不新增内存或执行扩容。测试同时固定源码和嵌入内核哈希；保留类型数组及显式小端 DataView 逆变换回退。

受支持的 HTTP 加载用 BYOB 字节读取器直接写入最终块缓冲，每次接回转移后的缓冲所有权。保持两个工作线程、每线程一个解码任务、七毫秒上传预算和完整资源就绪条件。首包不可用或传输不受支持时，在开始解码前使用原独立块加载器；后续包失败仍终止加载，不增加跨任务重试或 HTTP 转脚本恢复。工作线程内的解码回退维持原边界。销毁时中止场景 IO、拒绝等待任务并终止线程，上下文恢复使用全新所有权。`file://` 沿用原脚本内嵌 gzip。校验固定的资源归档必须保留全部原资源与官方解码器许可。

## 发布

同步更新 `VERSION`、包版本和页面版本。按需重建场景后，运行 `npm run assets:pack`，将资源包上传到对应 GitHub Release。

维护发布与渲染改动分别验证。运行时代码仅改版本号时，可将生成文件与上一版逐项比较，只排除确切的版本字符串、随内容变化的脚本文件名及构建元数据，并核对资源包和干净源码构建。该检查不能用于验收实验渲染器，也不能替代其画面、生命周期和性能验证。发布说明应区分本次新测结果与保留的历史证据。

运行 `npm run deploy` 构建网页并推送到 `gh-pages`，GitHub Pages 会从该分支发布到 `https://sldyns.github.io/PKU-3D/`。`main` 保存可编辑源码，`gh-pages` 只保存生成的网站。发布需要该仓库的 Git 推送权限。

发布脚本使用不含旧资源 blob 的部分克隆，不检出旧网站文件，禁用延迟下载与重命名识别，并通过受限打包执行普通快进推送。文件系统支持时以写时复制共享生成资源，否则使用普通复制。脚本仍会暂存完整生成目录，因此本次构建移除的文件也会从发布分支移除。本地部分克隆测试覆盖更新、删除和内容未变的再次发布。
